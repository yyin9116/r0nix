# 产品痛点与开发优先级

## 产品判断

### 当前进度

- P0-1：已完成可见页/overscan 内容挂载、分段块提取和 1000 页后端专项验证；页面占位保留滚动定位，缩放和滚动不再为所有页面挂载 PDF.js 子树；侧栏和阅读模式切换保留当前页视口锚点，不再强制居中造成跳动。
- P0-2：已完成 xref 原始图片提取和兼容当前 PyMuPDF 的 SVG 局部导出；页面裁剪、矢量区域和原始资源在导出链路中分开处理，并有真实嵌入 Python 集成测试。原始 xref 导出不再先渲染整页 PNG，顶部图片菜单和右键图片菜单均按当前页懒加载资源；宽幅/条带型 raster 资源不再因过严宽高比过滤而漏检。
- P0-3：已完成普通视图选择层隔离；全文辅助高亮按 PDF.js text layer 聚合为双栏内的段落级块，并携带块引用几何；列边界来自整层 spans，hover 矩形按连续文字片段拆分，避免短行宽度截断后续长行、跨行或跨栏填充空白。
- P1-1：已落地稳定 `documentId`、阅读块 ID、笔记和标注来源矩形；笔记与标注点击后会按来源矩形回到原文位置。
- P1-2/P1-3：Markdown 对照翻译已使用 `marked` GFM lexer 和共享的结构化 block parser，覆盖标题、嵌套列表、表格对齐、引用、数学块、代码和正文；HTML 以不可执行文本保留，脚注定义恢复为可定位的辅助块，避免内容静默丢失和文档内容注入 DOM。
- P1-4：资源索引已有进度、取消、缓存、增量跳过和失败重试；资源侧栏使用独立的 PDF.js 页级扫描队列，最多 3 页并发读取链接、文本和图片，不会隐式启动全文阅读块抽取；缓存带版本、字段校验和容量上限。图片标注和图片导出仍只按当前页/相邻页补齐阅读块。
- P1-5：翻译缓存已按稳定文档 ID、服务端点、模型、提示词、温度、目标语言和 block 结构指纹隔离；全文块提取支持取消信号。

长任务边界补充：全文搜索按页检查取消状态，切换文档或离开阅读器不会继续扫描旧 PDF；缺少 PDF.js 文档时阅读块加载会显式失败，避免把基础设施错误显示为空结果。

r0nix 当前最有价值的方向是“本地优先的 AI 科研阅读工作台”，核心闭环应保持为：

```text
打开论文 -> 结构化阅读 -> 选中段落 -> 翻译/提问 -> 保存引用 -> 回到原文
                         |
                         +-> 图片、链接、DOI 资源 -> 导出或继续研究
```

PDF 阅读器、Markdown 编辑器、图片导出和模型服务都服务于这条闭环。当前主要风险不是功能数量不足，而是三者还没有共享稳定的文档块、资源和引用模型。

## P0：发布前必须解决

### P0-1 PDF 长文档稳定性

- 痛点：全部页面容器一次性创建；页面尺寸、缩放和资源扫描在大 PDF 上仍有明显成本。
- 影响：论文页数越多，打开、滚动、缩放和切换资源越容易卡顿或超时。
- 代码边界：`PDFViewer.tsx` 页面挂载与 active page；`pdfJsService.ts` 文档缓存；`pdfApi.ts` 长任务适配。
- 方案：页面占位高度 + 可见页虚拟化；前后各保留有限 overscan；资源和块提取使用可取消队列。
- 验收：100、500、1000 页样本均可打开；滚动不创建全量 canvas；缩放期间不跳页、不出现空白页；任务可取消。
- 当前证据：后端 1000 页分段测试、前端 E2E、macOS release `.app` 启动和 PDF.js 开发运行链路均已通过；GitHub Actions run `32553879761` 已完成 Windows 安装 smoke、macOS bundle/DMG 构建和 artifact 上传；真实 100/500/1000 页 GUI 帧率基准仍是发布前的测量项。
- 打开失败边界：PDF.js 无法加载时会释放 Rust PDF handle 并显式失败，避免多个损坏或不兼容 PDF 叠加后持续占用资源。
- 打开性能边界：`open_pdf` 只做文件元数据登记；PyMuPDF 页数由 `get_page_count` 按需解析并缓存，避免打开阶段重复扫描大 PDF。页数任务仍属于可取消队列的后续优化范围。
- 页数失败边界：按需页数解析超过 30 秒会显式失败。阅读块提取已支持请求 ID 和 PyMuPDF 页/block 边界协作取消；底层单次 PyMuPDF 调用仍可能在当前 native 调用返回前完成收尾。
- 性能补充：首屏 tab 与 PDF.js 均按需加载，生产首屏主 chunk 已降至约 380 KB；嵌入 Python runtime 禁止在 Tauri 监视目录写入 `__pycache__`，避免首次解析 PDF 触发原生开发进程重编译；大文档真实 GUI 帧率仍需在桌面 runner 测量。

### P0-2 PDF 图片导出语义正确

- 痛点：当前“导出图片”主要是整页 PNG/SVG 后按 bbox 裁剪，不等同于原始图片资源。
- 影响：导出结果可能带入周边内容、分辨率不符、透明通道丢失，用户无法判断导出内容是否可靠。
- 代码边界：`py_render.rs` 图片识别与资源提取；`rustPdf.ts` 导出适配；`PDFViewer.tsx` 菜单和命名。
- 方案：明确区分“导出原始图片”“导出页面选区”“导出矢量图”；xref 图片走真实资源提取，裁剪只作为 fallback。
- 验收：PNG/JPG 等嵌入图片保留原始像素和透明度；矢量图不扩大到整页；导出文件名包含页码、资源 ID 和类型；失败有明确原因。

### P0-3 阅读块与文本选择一致

- 痛点：后端块 bbox、PDF.js text layer 和 hover 高亮可能出现范围不一致。
- 影响：段落只选中一半、右侧列缺失、引用文本与画面不一致，直接破坏 Ask AI 和翻译可信度。
- 代码边界：`pdfBlocks.ts`、`PDFViewer.tsx` text layer、块提取归一化。
- 方案：text layer 作为显示和选择的几何事实来源；后端块只提供稳定 ID、类型和 fallback；双栏、表格、标题分别建模。
- 验收：双栏论文、表格、标题、脚注各有 golden fixture；hover 矩形覆盖完整段落；点击后的文本与可见段落一致。
- 当前证据：普通视图已回归 PDF.js 原生 text layer，全文辅助块使用可见 text layer 聚合；双栏、跨行和间距分段几何 fixture 已加入 `test:pdf-blocks`，桌面端真实 PDF 的人工回归仍需在解锁的 macOS/Windows runner 上补齐，不能仅以 smoke test 代替。
- hover 性能边界：Full translation 命中优先消费 PDF.js 原生事件 target，几何扫描仅作为空白间隙 fallback；真实桌面论文 hover 帧率仍需 runner 测量。

## P1：核心体验必须补齐

### P1-1 统一 Document / Block / Asset / Reference 模型

- 痛点：PDF、Markdown、笔记、翻译缓存和图片资源分别按路径、页码或文本保存。
- 影响：无法稳定实现 PDF 段落到 Markdown 笔记、Markdown 回跳 PDF、资源回跳原文和对照翻译同步。
- 方案：每个文档产生稳定 `documentId`；每个段落、图片、链接和 DOI 产生 `blockId/resourceId`；笔记和翻译只引用这些 ID。
- 验收：删除或重开 tab 不改变引用目标；PDF 引用可以回跳页码和 bbox；Markdown 引用可以回到源 PDF；同一资源不会重复生成。

### P1-2 Markdown 标准兼容与结构化编辑

- 痛点：当前自定义渲染只覆盖标题、普通段落、简单列表、代码和链接。
- 影响：表格、引用、图片、数学公式和 GFM 文档会显示错误或丢失结构。
- 方案：引入成熟 Markdown AST/rendering 边界；编辑器保留纯文本编辑能力，预览、翻译和阅读辅助共享 AST 节点 ID。
- 验收：常见 GFM fixture 渲染稳定；保存前后内容字节不被重写；翻译不改变标题、列表、代码和图片结构。

### P1-3 Markdown 对照翻译真正按节点对应

- 痛点：当前翻译块会压平 Markdown 段落，并把所有块标记为 page 1。
- 影响：对照翻译无法定位原文结构，代码和标题不能正确处理。
- 方案：以 AST 节点为翻译单元；记录节点类型、路径、源文本和译文；代码块默认跳过，标题和列表保留结构。
- 验收：翻译结果可逐节点重试；源文档修改后只失效受影响节点；缓存不会把旧文档结构套到新文档。

### P1-4 资源索引可取消、可增量、可解释

- 痛点：资源侧栏需要覆盖整篇 PDF，但不能阻塞阅读块、翻译或首屏渲染；长文档扫描还需要明确的中止和失败反馈。
- 方案：独立资源索引任务，限制并发，记录 `queued/running/ready/failed/cancelled`，完成一页就写入状态和缓存；链接、DOI 文本和图片使用 PDF.js 页级数据，全文阅读块只由阅读/翻译路径按需加载。
- 验收：资源侧栏立即可见；扫描进度可见；关闭侧栏可取消；失败页面可重试；已有结果无需重复扫描。

### P1-5 LLM 缓存和配置隔离

- 痛点：缓存 key 不能完整区分 base URL、system prompt 和温度参数。
- 影响：切换 LiteLLM 服务或提示词后可能展示旧译文。
- 方案：缓存 key 纳入服务端点、模型、目标语言、提示词版本/hash、temperature 和源块指纹。
- 验收：任一配置变化都会命中正确缓存或重新请求；缓存损坏不会阻塞阅读；缓存大小和清理策略可见。

## P2：形成产品壁垒

- 多文档对比：按 block 对齐原文、译文和方法差异。
- 研究笔记：引用携带 `documentId/blockId/page/bbox`，支持双向回跳。
- 资源工作流：图片、表格、公式、链接、DOI 进入统一资源面板并支持导出。
- 画布联通：白板卡片引用阅读块，而不是复制一段失去来源的文本。
- 本地检索：跨 PDF、Markdown、笔记和资源统一搜索。
- 术语表和引用格式：让翻译和论文整理结果可复用。

## 发布门槛

在 P0 未完成前，不建议以“成熟 PDF 阅读器”或“通用 Markdown 编辑器”进入应用市场。更准确的早期定位是：

> 面向论文和技术资料的本地优先 AI 阅读工作台。

首个市场版本应只突出三件事：

1. PDF 段落级阅读与 Ask AI/翻译；
2. 图片、链接、DOI 等资源的可追溯导出；
3. 引用沉淀为 Markdown 研究笔记并可回跳原文。

应用商店发布前还必须验证文件权限、模型请求隐私、Python/PyMuPDF 运行时、WebView 权限、签名公证和大文档资源占用。未配置模型时，PDF 阅读、选择、资源识别、笔记和导出仍必须完整可用。
